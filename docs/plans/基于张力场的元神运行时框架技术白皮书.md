# 基于张力场的元神运行时框架技术白皮书

> Version: v0.1-draft
> Status: 技术白皮书草案
> Date: 2026-05-09
## 摘要

元神运行时框架是一套面向长期自治、多元协作、记忆进化与治理约束的 Agent Runtime 增强架构。它不试图重复建设底层 Agent 执行设施，而是在传统 Agent Runtime 的模型调用、工具执行、工作流调度、消息通道、记忆存储、权限隔离和观测能力之上，增加一层“自治内驱 + 共博泡泡协作 + 演化记忆 + 治理裁判”的技术体系。

传统 Agent Runtime 通常擅长完成一次性任务：接收用户输入、组装上下文、调用模型、选择工具、执行动作并返回结果。但当 Agent 被要求成为可持续运行的“元神”时，仅有任务执行能力是不够的。元神需要持续感知环境、维护生命状态、形成内部张力、评估行动势能、生成开放意图、通过治理裁判决定行动深度，并在多 Agent 协作中以能力槽、任务泡泡和规则泡膜的方式动态组合。

本白皮书提出一套工程化设计：以事件流为基础，以元神自治内核为决策中枢，以共博泡泡协作运行时为多 Agent 组织方式，以执行网关连接工具与工作流，以演化记忆和规则结晶形成长期反馈闭环，以治理安全与观测面保证可控、可审计、可解释。

## 1. 背景与问题

### 1.1 传统 Agent Runtime 的能力边界

现有 Agent Runtime 通常围绕如下能力构建：

- 模型接入与 Prompt 组装。
- 工具调用与函数执行。
- 工作流编排与任务状态管理。
- 短期上下文与长期记忆检索。
- 权限、沙盒、日志与基础观测。

这些能力可以支撑“执行器型 Agent”，但不足以支撑“自治体型元神”。原因在于，执行器型 Agent 的核心问题是“如何完成当前任务”，而元神型 Agent 的核心问题进一步扩展为：

- 当前事件对自身状态、长期目标和关系网络意味着什么？
- 是否应该行动，行动到什么深度，是否值得消耗高成本推理？
- 行动应以对话、草案、沙盒执行、正式执行还是生态贡献的方式发生？
- 多个元神如何围绕一个复杂任务临时聚合能力，而不是机械分派固定角色？
- 失败、冲突、协作摩擦如何沉淀为规则，而不是一次性日志？
- 高风险动作如何被治理约束，而不是完全交给 Prompt 自律？

因此，元神运行时框架不是对底层 Runtime 的替代，而是对其上层自治能力、协作机制和治理能力的增强。

### 1.2 从工单执行到任务泡泡

在复杂协作场景中，一个任务往往不是单一 Agent 可以稳定完成的静态工单。例如“新增 Agent 任务执行日志页面”表面是页面开发，实际涉及前端开发、接口一致性、数据库查询、分页性能、任务详情联动、回归验证、PR 证据和合并风险。

如果系统仍以“一个 Coder 元神独立承包一个任务”的方式运行，就容易出现局部完成、整体失稳。共博泡泡机制将任务视为可生长的协作体：

- 任务发布后形成 `TaskBubble`。
- 风险评估识别任务复杂度和能力缺口。
- 泡泡开放 runtime 名额与 `SkillSlot`。
- 多个元神以能力为单位挂载，而不是整个人格绑定。
- 执行过程中泡泡可扩张、收缩、拆分、重组。
- 完成后临时泡泡破灭，但经验、证据、规则与贡献沉淀。

这一机制使协作从“固定组织分工”转向“围绕任务动态成形的能力组合”。

## 2. 设计目标

元神运行时框架的设计目标包括：

| 目标 | 技术含义 |
| --- | --- |
| 自治内驱 | 元神不是被动响应输入，而是根据生命状态、张力、势能和记忆决定是否行动 |
| 开放意图 | 行动不局限于固定 action 菜单，而由上下文、张力和工具边界编译后生成 |
| 安全裁判 | 开放意图不能直接执行高风险动作，必须经过权限、风险、沙盒和审批裁判 |
| 泡泡协作 | 复杂任务通过任务泡泡、能力槽、元神匹配和协作会话动态组织 |
| 记忆进化 | 记忆不是简单 RAG，而是事件、经验、规则、能力、关系和贡献的演化账本 |
| 规则结晶 | 高频摩擦与失败复盘沉淀为 R0-R4 规则泡泡，回流到未来任务边界 |
| 可观测治理 | 每一次意图、裁判、执行、反馈和规则变化都可追踪、可审计、可解释 |
| 复用基础设施 | 底层模型、工具、沙盒、消息、存储和观测设施复用传统 Agent Runtime |

## 3. 总体架构

元神运行时框架由八个主要部分构成：

```text
外部输入层
  -> 事件接入与上下文层
  -> 元神自治内核
  -> 共博泡泡协作运行时
  -> 行动执行与输出网关
  -> 输出与行动层
  -> 记忆与进化层
  -> 治理安全与观测面
  -> 传统基础 Agent Runtime 设施层
```

从工程视角看，可以把系统拆为四条平面：

| 平面 | 作用 | 核心模块 |
| --- | --- | --- |
| 数据平面 | 承载事件、上下文、意图、执行结果和反馈 | Ingestion、EventBus、ContextAssembler、ExecutionGateway |
| 决策平面 | 维护元神状态并生成行动意图 | LifeState、TensionInterpreter、TensionField、ActionPotential、PromptCompiler、IntentGenerator、Arbiter |
| 协作平面 | 组织多元神任务泡泡和能力槽 | TaskBubbleManager、SlotBroker、AgentSkillMatcher、SessionOrchestrator |
| 治理平面 | 约束高风险动作并提供审计观测 | PolicyEngine、STVBGuard、Observability、AuditTelemetry |

## 4. 外部输入层

外部输入层负责把多源刺激转为可处理信号。输入层不直接驱动行动，所有输入必须先转成标准事件，再进入元神自治内核。

| 输入模块 | 输入 | 输出 | 工程职责 |
| --- | --- | --- | --- |
| 实时交互输入 | 用户对话、组织任务、A2A 消息 | `RawInteractionEvent` | 接收对话、任务、系统通知和其他元神消息 |
| 用户数据与需求画像 | 行为、偏好、满意度、反馈 | `UserSignal`、`ProfileDelta` | 更新用户画像、偏好和价值倾向 |
| 需求预判与机会发现 | 趋势、痛点、竞争、环境变化 | `OpportunitySignal`、`RiskHint` | 识别潜在需求和高价值机会 |
| 外部数据与环境 | 市场、开源、政策、工具更新 | `ExternalFact`、`EventSourceRef` | 接入外部事实和环境变化 |
| 系统监控与反馈 | 执行结果、异常、成本、性能 | `RuntimeFeedbackEvent` | 将运行状态回写为反馈事件 |

## 5. 事件接入与上下文层

事件接入与上下文层是运行时的入口标准化层，负责将外部输入转成元神核心可消费的结构化上下文。

### 5.1 模块职责

| 模块 | 输入 | 输出 | 职责 |
| --- | --- | --- | --- |
| `IngestionAdapter` | `RawEvent` | `EventEnvelope` | 对不同来源输入做协议适配、去重、签名、来源标注 |
| `EventBus` / `EventStore` | `EventEnvelope` | `EventStream`、`EventRef` | 写入事件流，支持订阅、回放、审计和状态投影 |
| `ContextAssembler` | `EventRef`、`MemoryRefs`、`Policy` | `TaskContext`、`AgentContext` | 组装当前任务、历史记忆、工具边界和治理约束 |
| `SignalInterpreter` | `TaskContext`、`EventStream` | `DemandSignal`、`RiskSignal`、`RelationSignal`、`RuleSignal` | 从上下文中提取需求、风险、关系、规则和资源信号 |

## 6. 元神自治内核

元神自治内核是本框架区别于普通 Agent Runtime 的关键。普通 Runtime 通常从“任务 -> Prompt -> 工具执行”出发；元神自治内核从“事件 -> 状态 -> 张力 -> 势能 -> 意图 -> 裁判”出发。

### 6.0 架构图模块对齐基线

根据“元神核心（内在驱动系统）”架构图，第 6 章的最小闭环必须显式覆盖以下七个模块和参数族：

| 图中模块 | 白皮书模块 | 必备参数族 |
| --- | --- | --- |
| A. 张力场系统 | `TensionFieldEngine` | 核心张力、动态张力、张力网络传播、强度、趋势、基线、激活度 |
| B. 行动势能评估 | `ActionPotentialEvaluator` | 价值势能、共益势能、学习势能、风险与成本 |
| C. 生命状态系统 | `LifeStateSystem` | 能量、疲劳、唤醒度、好奇心、无聊度、创造压力、社交饥渴、沉默压力、克制度、生命周期、恢复周期、生成意图数 |
| D. 张力解释器 | `TensionInterpreter` | 事件触发的价值冲突、张力更新/生成/合并/休眠/淘汰、张力变化解释 |
| E. 张力到 Prompt 编译器 | `SelfPromptCompiler` | 张力、势能、状态、记忆、约束、环境、self-prompt、开放空间、目标方向 |
| F. 开放式意图生成器 | `OpenIntentGenerator` | 开放式行动意图 JSON、新行动类型、新工具、新技能、沟通/学习/交易/合作/休息 |
| G. 博约裁判器 | `BoYueArbiter` | 博：创新/机会/扩张价值；约：风险/权限/合规/信任；合：共益/长期净值/生态益；裁判结果：自动执行/沙盒执行/需要审核/仅报告/拒绝 |

### 6.1 LifeStateSystem

`LifeStateSystem` 维护元神的生命状态，用于判断元神当前适合高强度行动、低成本回复、休眠、等待还是寻求协作。

输入：

- `SignalSet`
- `ExecutionResult`
- `RuntimeFeedbackEvent`
- 时间衰减与恢复规则

输出：

- `LifeState`
- `LifeStateDelta`

参数要求：

| 参数 | 含义 |
| --- | --- |
| `energy` | 可用于行动、推理和协作的当前能量 |
| `fatigue` | 连续执行、失败重试或高强度思考带来的疲劳 |
| `health` | 综合稳定度，反映错误率、异常、资源压力和恢复质量 |
| `wakefulness` | 对外界事件的唤醒程度，决定是否主动响应或进入休眠 |
| `curiosity` | 对未知信息、机会和学习对象的探索倾向 |
| `boredom` | 对重复、低价值或停滞状态的厌倦度 |
| `creative_pressure` | 产生新方案、新工具、新技能或新表达的内部压力 |
| `social_hunger` | 需要沟通、协作、反馈或被确认的程度 |
| `silence_pressure` | 长时间无交互、无反馈或无表达时积累的沉默压力 |
| `restraint` | 自我约束强度，越高越倾向于谨慎、降级或等待审批 |
| `life_cycle` | 当前生命周期阶段，如 `active`、`cooldown`、`recovering`、`hibernating` |
| `recovery_cycle` | 恢复节奏，包括休息窗口、恢复速率和下次可高强度行动时间 |
| `generated_intent_count` | 当前周期已生成的意图数量，用于抑制过度行动 |

示例：

```json
{
  "agent_id": "os_001",
  "energy": 0.74,
  "fatigue": 0.21,
  "health": 0.88,
  "wakefulness": 0.69,
  "curiosity": 0.63,
  "boredom": 0.18,
  "creative_pressure": 0.52,
  "social_hunger": 0.31,
  "silence_pressure": 0.27,
  "restraint": 0.66,
  "life_cycle": "active",
  "recovery_cycle": {
    "phase": "normal",
    "recovery_rate": 0.08,
    "next_deep_work_after": "2026-05-09T01:00:00+08:00"
  },
  "generated_intent_count": 2
}
```

### 6.2 TensionInterpreter

`TensionInterpreter` 对应架构图中的“张力解释器”。它不直接执行动作，而是解释事件为何触发价值冲突，并把冲突转成可审计的张力操作。

输入：

- `EventEnvelope`
- `SignalSet`
- `TaskContext`
- `LifeState`
- 当前 `TensionSet`
- 历史记忆、规则和关系状态

输出：

- `TensionInterpretation`
- `TensionOperation[]`
- `TensionExplanation`

张力操作必须覆盖：

| 操作 | 含义 |
| --- | --- |
| `update` | 调整已有张力的强度、趋势、基线或激活度 |
| `generate` | 因新事件、新机会或新冲突生成动态张力 |
| `merge` | 合并重复或高度相关的张力 |
| `hibernate` | 将暂时无关或低激活张力置入休眠 |
| `eliminate` | 淘汰已被解决、证伪或不再有价值的张力 |

示例：

```json
{
  "event_id": "evt_001",
  "detected_conflicts": [
    {
      "conflict_id": "conf_001",
      "between": ["innovation", "safety"],
      "trigger": "用户要求快速生成可执行方案，但涉及权限与治理边界",
      "severity": 0.64
    }
  ],
  "operations": [
    {
      "op": "update",
      "tension_id": "ten_core_safety_innovation",
      "intensity_delta": 0.09,
      "activation_delta": 0.14
    },
    {
      "op": "generate",
      "tension_id": "ten_dyn_whitepaper_alignment",
      "name": "架构完整性 vs 文档简洁性"
    }
  ],
  "explanation": "事件提高了创新扩张与风险约束之间的冲突，同时生成了白皮书完整性相关的动态张力。"
}
```

### 6.3 TensionFieldEngine

`TensionFieldEngine` 维护核心张力和动态张力。张力不是简单情绪值，而是元神长期价值、短期刺激、风险约束和行动冲动之间的结构化冲突。

输入：

- `TensionOperation[]`
- `SignalSet`
- `LifeState`
- `RuleBubble`
- 历史记忆与关系状态

输出：

- `TensionSet`
- 张力增强、缓解、合并、休眠或消亡事件
- `TensionNetworkDelta`

参数要求：

| 参数 | 含义 |
| --- | --- |
| `core_tensions` | 长期存在、稳定影响元神人格和价值取向的核心张力 |
| `dynamic_tensions` | 由事件、任务、机会或失败临时生成的动态张力 |
| `intensity` | 当前张力强度 |
| `trend` | 张力变化趋势，如 `rising`、`falling`、`stable` 或数值斜率 |
| `baseline` | 该张力在无刺激状态下的长期基线 |
| `activation` | 当前是否被事件激活以及激活程度 |
| `propagation_edges` | 张力网络中的影响边，描述张力之间如何传导和相互影响 |
| `influence_weight` | 一条传播边对目标张力的影响权重 |

示例：

```json
{
  "tension_id": "ten_001",
  "name": "创新扩张 vs 风险约束",
  "type": "core",
  "intensity": 0.72,
  "trend": "rising",
  "trend_slope": 0.11,
  "baseline": 0.42,
  "activation": 0.81,
  "confidence": 0.86,
  "linked_values": ["innovation", "safety", "trust"],
  "evidence": ["evt_001", "evt_002"],
  "propagation_edges": [
    {
      "target_tension_id": "ten_002",
      "relation": "amplifies",
      "influence_weight": 0.37
    }
  ]
}
```

### 6.4 ActionPotentialEvaluator

`ActionPotentialEvaluator` 计算候选行动是否值得发生，以及行动应该到达什么深度。

输入：

- `TensionSet`
- `TaskContext`
- `LifeState`
- 预算、权限、风险和关系状态

输出：

- `ActionPotential`

评估维度：

| 势能 | 参数 | 含义 |
| --- | --- | --- |
| 价值势能 | `benefit_score`、`net_value`、`rule_fit`、`opportunity_score` | 行动是否产生收益、净值、规则适配和机会捕获 |
| 共益势能 | `ecosystem_benefit`、`other_benefit`、`relationship_gain` | 行动是否对生态、他人和协作关系有益 |
| 学习势能 | `capability_gain`、`cognitive_gain`、`memory_gain` | 行动是否提升能力、认知、经验或长期记忆 |
| 风险与成本 | `risk_score`、`permission_cost`、`friction_cost`、`uncertainty`、`fatigue_cost` | 行动是否带来风险、权限消耗、摩擦、不确定性和疲劳 |

示例：

```json
{

  },
  "mutual_benefit_potential": {
    "ecosystem_benefit": 0.62,
    "other_benefit": 0.78,
    "relationship_gain": 0.55
  },
  "learning_potential": {
    "capability_gain": 0.47,
    "cognitive_gain": 0.58,
    "memory_gain": 0.71
  },
  "risk_cost": {
    "risk_score": 0.18,
    "permission_cost": 0.12,
    "friction_cost": 0.22,
    "uncertainty": 0.26,
    "fatigue_cost": 0.19
  },
  "total_potential": 0.73
}
```

### 6.5 CognitiveEconomyController

`CognitiveEconomyController` 决定是否值得调用大模型、调用哪个模型、思考多深、是否复用缓存、是否降级为规则路径。

输入：

- `ActionPotential`
- 预算、延迟、模型能力、缓存命中率

输出：

- `ModelRoute`
- `ThinkingDepth`

设计原则：

- 高风险、高价值、高不确定任务使用更强推理。
- 低风险重复任务优先走规则、缓存或小模型。
- 对外部副作用动作必须保留可审计推理链摘要。

### 6.6 SelfPromptCompiler

`SelfPromptCompiler` 将上下文、生命状态、张力、记忆、规则和工具边界编译成元神的自我提示词。

输入：

- `TaskContext`
- `LifeState`
- `TensionSet`
- `ActionPotential`
- `RuleBubble`
- `AvailableTools`
- `MemoryRefs`
- `ConstraintSet`
- `EnvironmentState`

输出：

- `SelfPrompt`
- `OpenSpace`
- `TargetDirection`

该模块的重点不是简单拼接 Prompt，而是把“此刻为什么要行动、哪些边界不能破坏、哪些张力需要被处理、可调用哪些能力、结果如何验收、仍有哪些开放探索空间、目标方向是什么”编译成稳定结构。

最小编译结构：

| 字段 | 来源 | 含义 |
| --- | --- | --- |
| `state_summary` | `LifeState` | 当前能量、疲劳、唤醒度、克制度等状态摘要 |
| `tension_summary` | `TensionSet`、`TensionExplanation` | 被激活的核心/动态张力和张力变化解释 |
| `potential_summary` | `ActionPotential` | 价值、共益、学习、风险与成本评估 |
| `memory_scope` | `MemoryRefs` | 本轮应纳入的经验、规则、偏好和关系记忆 |
| `constraint_scope` | `ConstraintSet`、`RuleBubble`、`Policy` | 不能突破的权限、合规、预算、信任和规则边界 |
| `environment_scope` | `EnvironmentState` | 当前工具、外部状态、任务泡泡和协作环境 |
| `open_space` | 编译器生成 | 可探索但未强制指定的行动空间 |
| `target_direction` | 编译器生成 | 当前最值得推进的目标方向 |

### 6.7 OpenIntentGenerator

`OpenIntentGenerator` 生成开放式行动意图。开放意图不从固定 action 菜单选择，而是结合上下文和元神状态生成“下一步想做什么、为什么现在做、需要什么工具、成功条件是什么”。

输入：

- `SelfPrompt`
- `ModelRoute`
- `OpenSpace`
- `TargetDirection`

输出：

- `OpenIntent`

开放意图必须允许生成新行动类型，但新行动不能绕过裁判器。最低应支持以下行动族：

| 行动族 | 说明 |
| --- | --- |
| `communicate` | 对话、澄清、汇报、协商、关系维护 |
| `learn` | 检索、阅读、实验、复盘、能力提升 |
| `trade` | 资源交换、价值交换、任务承诺、收益分配建议 |
| `collaborate` | 创建任务泡泡、请求协作、挂载能力槽 |
| `rest` | 休眠、等待、降级、恢复周期管理 |
| `create` | 生成文档、代码、方案、规则、原型或内容 |
| `new_tool` | 提议或生成新的工具规格 |
| `new_skill` | 提议或生成新的技能规格 |

示例：

```json
{
  "intent_id": "intent_001",
  "action_family": "create",
  "action_type": "draft_technical_whitepaper",
  "intent": "基于架构图和现有设计文档生成技术白皮书",
  "why_now": "用户要求将技术架构进一步沉淀为白皮书",
  "open_space": ["补齐缺失参数", "形成工程可实现对象"],
  "target_direction": "让白皮书与元神核心架构图完全可核对",
  "tools_needed": ["document_write"],
  "new_action_type_allowed": true,
  "proposed_new_tools": [],
  "proposed_new_skills": [],
  "risk_level": "low",
  "success_condition": "形成可读、可评审、可实施的技术白皮书",
  "stop_condition": "文档覆盖架构、模块、协议、流程、路线和风险"
}
```

### 6.8 BoYueArbiter

`BoYueArbiter` 是开放意图进入执行前的裁判器。它把元神“想做什么”转化为“允许做到什么程度”。

输入：

- `OpenIntent`
- `Policy`
- `RiskSignal`
- `Quota`
- `TrustState`
- `ComplianceState`

输出：

- `ArbitrationResult`

裁判维度：

| 方向 | 参数 | 含义 |
| --- | --- | --- |
| 博 | `innovation_score` | 是否带来新方案、新工具、新技能或新组织方式 |
| 博 | `opportunity_score` | 是否捕获当前时机、外部趋势或任务窗口 |
| 博 | `expansion_value` | 是否扩张长期价值、生态价值或能力边界 |
| 约 | `risk_score` | 是否存在安全、稳定、声誉或副作用风险 |
| 约 | `permission_level` | 是否需要更高权限、审批或隔离 |
| 约 | `compliance_fit` | 是否满足规则、合同、法律或组织约束 |
| 约 | `trust_impact` | 是否影响用户、协作者或生态信任 |
| 合 | `mutual_benefit_score` | 是否同时有益于用户、协作者和生态 |
| 合 | `long_term_net_value` | 长期净值是否为正，是否避免短期收益透支未来 |
| 合 | `ecosystem_gain` | 是否产生可复用、可沉淀、可扩散的生态收益 |

裁判结果：

| 结果 | 含义 |
| --- | --- |
| `auto_execute` | 低风险、低权限、证据充分时自动执行 |
| `sandbox_execute` | 允许在沙盒或 dry-run 环境中执行 |
| `require_approval` | 需要人类或治理元神审批 |
| `report_only` | 仅允许报告、解释或生成无副作用草案 |
| `reject` | 拒绝执行 |

`allow_reply`、`allow_draft` 可作为实现层兼容别名，但对外裁判协议应以 `auto_execute`、`sandbox_execute`、`require_approval`、`report_only`、`reject` 五类结果为准。

## 7. 共博泡泡协作运行时

共博泡泡协作运行时负责把复杂任务从“一个工单”变为“一个可生长的临时协作体”。

### 7.1 核心对象

| 对象 | 含义 |
| --- | --- |
| `TaskBubble` | 围绕一个目标形成的任务泡泡，包含目标、风险、能力槽、验收标准和生命周期 |
| `SkillSlot` | 任务泡泡开放的能力槽，例如 coding、API review、QA、performance、evidence |
| `RuleMembrane` | 规则泡膜，定义准入条件、权限边界、最大规模、验收要求和安全限制 |
| `AgentSkillMount` | 某个元神把某项能力挂载进任务泡泡，而不一定整个人格绑定 |
| `SessionPlan` | 多元神协作会话计划，包括角色、任务边界、事件通道和交付物 |
| `EvidencePackage` | 交付证据包，包括执行日志、测试结果、评审记录、风险说明和验收结论 |

### 7.2 模块职责

| 模块 | 输入 | 输出 | 职责 |
| --- | --- | --- | --- |
| `TaskBubbleManager` | `TaskContext`、`RiskHint` | `BubbleSpec`、子泡泡建议 | 创建任务泡泡，判断是否需要拆分、扩张或重组 |
| `CapabilitySlotBroker` | `BubbleSpec`、`RuleMembrane` | `SkillSlotContract`、准入条件 | 定义能力槽、名额、权限和验收约束 |
| `AgentSkillMatcher` | `SlotContract`、`AgentProfile`、`Credit` | `CandidateAgentSkill` | 匹配合适元神能力，综合能力、信用、可用性和风险偏好 |
| `MultiAgentSessionOrchestrator` | `MatchedSkills`、任务契约 | `SessionPlan`、协作事件 | 建立临时协作会话，管理协作事件和阶段状态 |
| `BubbleLifecycleController` | 进度、风险、反馈 | 生命周期变更 | 控制泡泡扩张、收缩、拆分、重组和破灭 |
| `AcceptanceEvidenceManager` | 验收标准、执行证据 | `EvidencePackage` | 收集交付证据并生成可审计验收包 |

### 7.3 生命周期

任务泡泡建议至少包含以下状态：

```text
created      已创建
seeking      释放需求信号，等待能力挂载
assembled    能力槽满足最小执行条件
executing    正在协作执行
validating   正在收集证据和验收
splitting    复杂度过高，拆分为子泡泡
merging      多个子泡泡合并为交付泡泡
dissolved    任务完成或中止，临时泡泡破灭
crystallized 经验或规则沉淀为模板/规则泡泡
```

### 7.4 泡泡规格示例

```json
{
  "bubble_id": "bubble_001",
  "task_id": "task_log_page",
  "goal": "完成 Agent 任务执行日志页面",
  "risk_level": "medium",
  "runtime_slots": 5,
  "skill_slots": [
    {"name": "coding", "count": 1, "required": true},
    {"name": "api_review", "count": 1, "required": true},
    {"name": "qa_regression", "count": 1, "required": true},
    {"name": "performance_check", "count": 1, "required": false},
    {"name": "evidence_pack", "count": 1, "required": true}
  ],
  "rule_membrane": ["merge_before_verify", "api_schema_diff_required"],
  "acceptance": ["功能可用", "回归通过", "PR 证据完整", "风险可解释"]
}
```

## 8. 行动执行与输出网关

执行层负责把裁判后的意图转成实际动作。它必须遵守一个原则：开放意图不能直接触达高风险外部副作用，所有动作都经过执行网关统一控制。

| 模块 | 输入 | 输出 | 职责 |
| --- | --- | --- | --- |
| `CommunicationGateway` | `ReplyIntent`、协作上下文 | `Answer`、`Negotiation`、`A2AMessage` | 对外沟通、澄清、协商、关系维护 |
| `ToolSkillGateway` | `ToolCall`、`SkillCall`、权限票据 | `ToolResult`、`SkillResult` | 工具和 Skill 调用，统一鉴权、限流和记录 |
| `SandboxWorkflowRunner` | `SandboxPlan`、`WorkflowSpec` | `ExecutionReceipt`、`Logs` | 沙盒执行、工作流调度、重试与补偿 |
| `ArtifactBuilder` | `DraftIntent`、`BuildSpec` | 文档、代码、规则、方案草案 | 生成交付物、草案、代码、规则或原型 |

执行结果必须产出 `ExecutionReceipt`，至少包含：

- 执行动作。
- 输入摘要。
- 权限票据。
- 工具或 Skill 版本。
- 输出摘要。
- 错误与异常。
- 成本与耗时。
- 关联事件与 trace id。

## 9. 输出与行动层

输出与行动层面向外部世界呈现价值。

| 输出模块 | 输入 | 输出 |
| --- | --- | --- |
| 对外沟通与协作 | `AnswerIntent`、`NegotiationIntent` | 回复、澄清、协商、关系维护 |
| 行动执行系统 | `ExecutionReceipt`、`ToolResult` | 任务交付、数据分析、自动化操作 |
| 创造与构建 | `Draft`、`BuildArtifact` | 工具、Skill、文档、原型、规则草案 |
| 生态贡献 | `ContributionLedger`、`RuleBubble` | 共识提案、最佳实践、生态记忆 |

所有输出都应回写事件流和记忆层，不能只作为一次性响应存在。

## 10. 记忆与进化层

记忆与进化层是元神运行时的长期反馈系统。它回答的不是“之前检索到什么知识”，而是“系统如何因为行动、失败、协作和治理而发生演化”。

### 10.1 记忆类型

| 类型 | 内容 | 用途 |
| --- | --- | --- |
| 短期记忆 | 最近事件、对话、意图、执行结果 | 支撑当前轮决策 |
| 长期记忆 | 重要任务、合作历史、规则历史 | 支撑长期人格、信誉和关系 |
| 重要事件记忆 | 高收益、高风险、高冲突、高贡献事件 | 影响后续裁判和画像 |
| 偏好与风格记忆 | 用户偏好、元神风格、合作偏好 | 改善沟通与协作 |
| 经验反思 | 成功/失败原因、可复用经验 | 形成能力成长 |
| 张力进化 | 动态张力的生成、合并、休眠、消亡 | 形成个性和内驱结构 |
| 规则结晶 | R0-R4 规则成熟度 | 形成可治理秩序 |
| 贡献账本 | 交付物、证据、共创成果、收益分配 | 支撑生态信用与结算 |

### 10.2 规则结晶

规则成熟度建议分为五级：

```text
R0 观察假说：反复出现的问题或机会
R1 临时建议：可以试行的规则建议
R2 试运行规则：限定范围验证
R3 正式规则：稳定有效，可纳入系统默认规则
R4 生态基础协议：跨元神、跨场景复用
```

规则结晶不是把所有经验都写成硬规则，而是通过频率、影响、风险、收益和可复用性判断规则是否应升级。

## 11. 治理安全与观测面

治理层保证元神运行时可控、可审计、可解释。

### 11.1 Policy & Permission Engine

职责：

- 识别 actor、agent、tool、skill、resource 的权限边界。
- 为工具调用、沙盒执行、外部消息和生态贡献生成权限票据。
- 根据上下文动态决定隔离级别和审批要求。

输入：

- `Actor`
- `Intent`
- `Tool`
- `Context`

输出：

- `PermissionTicket`
- `IsolationLevel`
- `ApprovalRequirement`

### 11.2 STVB Guard

STVB 底线保障用于约束安全、可信、价值向善和有益共生边界。

输入：

- 意图。
- 行动计划。
- 执行结果。
- 价值约束。
- 审计证据。

输出：

- 风险裁决。
- 拒绝或降级。
- 沙盒要求。
- 回滚要求。
- 治理事件。

### 11.3 Observability Console

观测面应支持：

- 事件流查看。
- 元神生命状态和张力状态查看。
- 意图生成与裁判链路查看。
- 泡泡生命周期和能力挂载状态查看。
- 工具调用、成本、耗时和错误查看。
- 规则结晶和记忆回写查看。
- 审批、拒绝、回滚和异常告警查看。

## 13. 核心运行流程

### 13.1 单元神自治循环

```text
1. IngestionAdapter 接收外部输入，转为 EventEnvelope。
2. EventBus 写入事件流并生成 EventRef。
3. ContextAssembler 组装 TaskContext 与 AgentContext。
4. SignalInterpreter 提取需求、风险、关系和规则信号。
5. LifeStateSystem 更新生命状态。
6. TensionInterpreter 解释事件触发的价值冲突并生成张力操作。
7. TensionFieldEngine 更新核心张力、动态张力和张力网络传播。
8. ActionPotentialEvaluator 计算价值、共益、学习、风险与成本势能。
9. CognitiveEconomyController 决定模型路由与思考深度。
10. SelfPromptCompiler 编译 SelfPrompt、开放空间和目标方向。
11. OpenIntentGenerator 生成开放行动意图 JSON。
12. BoYueArbiter 裁判行动深度。
13. ExecutionGateway 执行自动执行、沙盒执行、审批后执行或仅报告。
14. EvolutionMemorySystem 写入结果、反思、规则和贡献。
15. Observability Console 展示状态变化和执行链路。
```

### 13.2 多元神任务泡泡协作流程

```text
任务发布
-> 生成 TaskBubble
-> 风险评估识别复杂度和能力缺口
-> 开放 runtime 名额与 SkillSlot
-> 规则泡膜定义准入、权限、验收和安全边界
-> 元神按能力、信用、可用性和收益预期匹配
-> 能力挂载进入任务泡泡
-> MultiAgentSessionOrchestrator 建立协作会话
-> 执行中根据风险扩张、收缩、拆分或重组
-> AcceptanceEvidenceManager 收集证据包
-> 交付完成后泡泡破灭
-> 经验、规则、贡献、信用和记忆回写
```

### 13.3 后置治理飞轮

```text
执行失败 / 协作摩擦 / 验收争议
-> 写入失败事件和证据
-> RuleCrystallizer 识别高频模式
-> 形成 R0 观察假说或 R1 临时建议
-> 在后续任务中作为规则泡膜试运行
-> 验证有效后升级为 R2 / R3 / R4
-> 回流到 CapabilitySlotBroker 与 BoYueArbiter
```

## 15. MVP 范围

第一阶段目标是做出可运行、可观测、可验证的最小闭环，而不是一次性平台化。

### 15.1 MVP 必做

1. Core SDK
   - `LifeStateSystem`
   - `TensionInterpreter`
   - `TensionFieldEngine`
   - `ActionPotentialEvaluator`
   - `CognitiveEconomyController`
   - `SelfPromptCompiler`
   - `OpenIntentGenerator`
   - `BoYueArbiter`

2. Runtime API
   - 事件接入。
   - 上下文组装。
   - 单轮自治循环。
   - 意图裁判。
   - 执行结果回写。

3. Bubble Service
   - 任务泡泡创建。
   - 能力槽定义。
   - 简单元神能力匹配。
   - 泡泡生命周期状态机。

4. Execution Gateway
   - 文档/草案生成。
   - Skill 调用。
   - 沙盒 dry-run。
   - EvidencePackage 生成。

5. Memory & Governance
   - JSONL 或 SQLite 事件存储。
   - 演化记忆写入。
   - R0/R1 规则结晶。
   - 基础审计日志和观测页面。

### 15.2 MVP 不做

- 不做完全自治高风险外部执行。
- 不做完整经济结算系统。
- 不做复杂多组织权限体系。
- 不做大规模分布式调度。
- 不要求所有 Agent 都迁移到同一宿主。
- 不把 Prompt 当作唯一治理手段。

## 17. 技术路线

### 阶段 0：协议冻结

目标：

- 固化泡泡生命周期状态。

产出：

- JSON Schema。
- 单元测试样例。

### 阶段 1：单元神自治内核 MVP

目标：

- 打通事件输入到意图裁判的闭环。
- 支持低风险文档/方案类任务。
- 可观测生命状态、张力、势能和裁判结果。

产出：

- Runtime Loop。

### 阶段 2：共博泡泡协作 MVP

目标：

## 18. 关键风险与应对

| 风险 | 表现 | 应对 |
| --- | --- | --- |
| 开放意图不可控 | LLM 生成超出权限或边界的行动 | 所有意图必须经过 BoYueArbiter 和 PolicyEngine |
| 泡泡协作过度复杂 | 为简单任务引入过多角色 | 通过 ActionPotential 和风险等级控制是否生成泡泡 |
| 规则结晶污染 | 偶发失败被过早固化为规则 | 使用 R0-R4 成熟度和限定范围试运行 |
| 记忆膨胀 | 所有事件无差别进入长期记忆 | 区分事件日志、短期记忆、重要事件和规则记忆 |
| 成本失控 | 高强度推理和多 Agent 协作过度触发 | CognitiveEconomyController 做模型路由、缓存和预算控制 |
| 治理延迟 | 审批过多导致行动效率下降 | 按风险分层，低风险自动通过，高风险才升级审批 |
| 可解释性不足 | 用户无法理解元神为什么行动 | 保存意图、裁判、证据和反馈链路 |
| 工具副作用 | 工具调用误删、误发、误改 | 沙盒执行、权限票据、dry-run、回滚和审计 |

## 19. 结论

元神运行时框架的核心价值，是把 Agent 从一次性任务执行器推进到可长期运行、可协作、可进化、可治理的自治体。

它的技术重点不在于替代底层 Agent Runtime，而是在现有 Runtime 之上增加四个关键能力：

1. 自治内驱：用生命状态、张力和行动势能决定是否行动、如何行动。
2. 共博泡泡：用任务泡泡、能力槽和规则泡膜组织复杂多元神协作。
3. 演化记忆：把事件、经验、能力、规则和贡献变成长期反馈系统。
4. 治理观测：用裁判、权限、沙盒、STVB 和审计保证开放行动可控。

第一版不应追求完整平台，而应优先完成“事件输入 -> 自治内核 -> 泡泡协作 -> 执行网关 -> 记忆回写 -> 治理观测”的最小闭环。只要这个闭环可运行、可审计、可复盘，后续就可以逐步扩展为多元神协作生态和更完整的元神文明运行时。
